### Security
- **Error responses no longer carry database, filesystem or upstream text.** Several API endpoints answered a failure with the raw error string, which could include a metadata provider's request URL with its API key and the resolver address, a SQL driver message, a filesystem path from a failed `stat`, or whatever page a download client or Prowlarr returned. They now answer with a fixed message and keep the detail in the Bindery log. This covers grab and retry of a queue item (and the per row results of a bulk retry or remove), the book rebind and audiobook enrich calls, the author relink calls, add book and adoption, adding a root folder (which still says whether the path is missing, unreadable or under a file), manual import paths and the Fix Match preview, the user role change, the migration uploads and the Audiobookshelf import and rollback calls. Download client and Prowlarr connection tests still say what went wrong, but only the first line, with credentials redacted, at most 200 characters, and an unreachable client is named with the host and port you configured. A paused metadata provider (daily quota or rejected token) still says so. Visible API changes: a grab or retry whose download client refuses the release or cannot be reached answers `502` with `failed to send the release to the download client`; a missing download client is a `400` with `"code": "no_download_client"` (the web app now keys on the code instead of the message text); a download client connection test that fails after reaching the client answers `502` instead of `400`; a rollback of an unknown Audiobookshelf run answers `404` and an unavailable one `503` instead of `400`; changing the role of an unknown user answers `404`; an oversized migration upload answers `413`. A Prowlarr test or sync that fails because the database is down now answers `500` instead of `404`.
